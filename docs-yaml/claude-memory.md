On 2026-08-04, told that hwprivacy's daemon burns 1.2% of a core at idle
(polling `pw-dump` twice a second), Costin's response was:

> "the price of 1.2% of a core is very generous. i wouldnt pay such a price."

**Why:** he treats always-on background cost as a first-class design
constraint, not an implementation detail. A 1.2% idle burn was enough to
invalidate an otherwise working architecture. Numbers like this decide
direction for him — so an unmeasured claim of "this is cheap" is worse than
useless, it can steer a whole build wrong.

**How to apply:**
- Measure before asserting overhead. Never say "negligible" from reasoning alone.
- When a number is not yet measured, **say so explicitly** and record it as
  outstanding rather than letting it become a silent assumption. This was done
  in `docs-yaml/ROADMAP.yaml > kernel_layer > outstanding_measurement`, marked
  `NOT YET MEASURED — do not claim it is cheap until it is`.
- Beware the tempting cheap fix that trades the wrong thing: raising
  `poll_interval_ms` buys CPU by widening a security race window. He wants the
  cost gone, not moved.

Still outstanding for hwprivacy: the eBPF LSM hook fires on **every** `open()`
system-wide and its cost has not been measured. Method: time ~200k
`open`/`close` of `/dev/null` with and without the program attached.

## feedback-prove-the-test-fails.md · type: feedback

---

metadata:

---

Before keeping a new test, reintroduce the defect it exists to catch and watch
it **fail**. A test that passes both ways is worthless, and this is not
theoretical here.

**Why:** on 2026-08-23 the first version of b3's direction-filter test passed
with the filter *removed*. On this laptop a sink's out-ports are `monitor_*`
and its in-ports are `playback_*`, and `monitor` sorts before `playback`, so
mixing the two populations produced the right ordinals by pure alphabetical
luck. The test was rewritten with a port that sorts first. Nothing but running
it against the bug would have found that.

Related: on the same day a `#[test]` attribute was found stacked twice on one
function, leaving the function below it with none. It compiled, it read as
covered, and it had never run once.

**How to apply:** after writing the test, edit the source to put the bug back
(one line is usually enough), run just that test, confirm FAILED, then revert
and confirm it passes. Do this for each distinct property, not once per file —
five defects were reintroduced separately across the b1/b2/b3 work and each one
mapped to a different failing test. Record in the commit message which defects
were reintroduced. See [[feedback-test-the-instrument-not-just-the-code]].

Built up over 2026-08-05 across three separate confusions, each of which cost a
run or a wrong conclusion. Now a global hard preference in `~/.claude/CLAUDE.md`.

**Who runs what — two axes, `sudo` and `test`. Costin's own formulation:**

    test + sudo  = Costin + banner
    sudo only    = Costin only        (no banner — nothing to interpret)
    test only    = Claude only        (Claude runs it and reads it)

Never hand over a script that does not need `sudo` — run it and report the
conclusion. The banner exists only where Costin must both EXECUTE and
INTERPRET. I first got this wrong twice: once narrowing it to sudo alone, once
widening it to the union. It is the intersection.

**A test+sudo script prints this before any work:**

```
  ─────────────────────────────────────────────────────────────
  HOW THIS ENDS:   <bound, or the named human action>
  RESULTS APPEAR:  <exactly one place — and what is NOT showing them>
  WHAT TO DO:      <paste the ==== marked block into the Claude chat>
  ─────────────────────────────────────────────────────────────
```

**Why each part exists — all three were learned the hard way:**

1. *How it ends* — Costin asked "should i stop it? with ctrl-c?" while an
   observer sat waiting. He cannot distinguish "still working" from "waiting
   for me". Earlier, guessing wrong, he started a mic event mid-benchmark to
   help and contaminated the measurement.
2. *Where results appear* — he asked, correctly, "what burst are you talking
   about? the terminal? firefox popups? the systray app?" I had been describing
   a future notification path as if it existed. **Name the one surface, and
   explicitly rule out the others** — a running tray icon showing unrelated
   events is worse than nothing.
3. *What to do with them* — he works in VS Code + the Claude Code extension and
   pastes output back into the chat. Wrap the pasteable part in
   `════ PASTE FROM HERE ════` / `════ TO HERE ════` so it is one selection.

**Make it a tested contract, not a comment.** In hwprivacy this is
`Cli::exit_condition()` / `results_location()` / `what_to_do()` in
`hwprivacy-lsm/src/main.rs`, with unit tests asserting each part names something
concrete — including that `results_location()` explicitly mentions the tray and
notifications as places results do NOT appear. Same reasoning as
[[feedback-measure-before-claiming-cheap]]: prefer a check that fails over a
discipline that must be remembered.

Supersedes the narrower [[feedback-announce-how-a-test-ends]], which covered
only the first part.

## feedback-test-the-instrument-not-just-the-code.md · type: feedback

On 2026-08-19, during hwprivacy kernel-layer testing, **four of my own
instruments failed in one evening while the product behaved correctly.** Costin
stopped one run himself with *"i think your proposed test is flawed"*, and he
was right.

**Why:** every one of these produced a confident wrong answer. A test that
reports a conclusion it has not established is worse than no test, because it
gets believed and redirects the whole investigation.

## The four failures, and their shared shape

1. Waited for the log line `attached to lsm/file_open` — which the `--json`
   flag suppresses. The wait could never succeed. It killed a working helper
   and reported it as broken.
2. & 3. Two `pkill -f` / `pgrep -f` patterns matched the **checking shell's own
   command line**. One killed my own process; one reported a helper "running"
   when none existed.
4. A test script killed the helper mid-push, so the request landed on a process
   already shutting down — then deleted the log proving it, because the log
   lived in a `mktemp` dir cleaned by an `EXIT` trap.

**The shape: asserting on log TEXT and on process-name patterns.** Both are
proxies that can be true or false for reasons unrelated to what is being
measured.

## How to apply

- **Assert on STATE, not on text.** Does the socket file exist. Does the kernel
  map hold the key. Is the `open()` actually denied. Text-matching a log line
  is a last resort, and if you must, check the string is reachable under the
  exact flags you are passing.
- **Never delete the raw evidence.** Write logs to a fixed path, not a
  `mktemp` dir with a cleanup trap. A summary chosen in advance only helps if
  you already guessed what mattered — and if you had, you would not have needed
  the run.
- **Suspect the harness first** when a result is surprising. Three separate
  times the product was correct and my measurement was not.
- **Do not make the user the sensor.** A test that asks "did you see video?"
  and provides nowhere to record the answer is broken. Where a human must
  observe, give the observation an explicit slot — and prefer driving it
  yourself (headless Chrome opened the real camera with no human at all).
- **Exclude confounds BEFORE the run, not by argument after.** Prove it by what
  is absent: run with no socket so the daemon *cannot* have helped; check
  nothing already holds the device so a retained fd *cannot* explain it.
- **Distinguish failure modes in error messages.** `recv_timeout` returns `Err`
  for both timeout and disconnect; reporting both as "timed out" made a 0.22s
  disconnect read as a 5s timeout and sent me hunting slow disk I/O that did
  not exist.

Related: [[feedback-test-contract-three-parts]] (how a test announces itself to
Costin), [[project-kernel-pivot]] (where this happened),
[[feedback-measure-before-claiming-cheap]] (the same "measure, don't assert"
instinct applied to cost).

On 2026-08-04 hwprivacy changed direction. It was built to police the PipeWire
graph; that was measured and found structurally blind to direct device access.
It now has **two enforcement layers behind one policy engine**:

- **PipeWire layer** (existing, running): monitor taps + per-app/per-stream mic.
  Genuinely works for the playback-monitor case, which has no kernel
  equivalent — keep it.
- **Kernel layer** (`hwprivacy-lsm`, `hwprivacy-proto`): eBPF LSM on
  `security_file_open`. Sees direct V4L2/ALSA access that PipeWire cannot.
  **Camera first; audio is a separate feature, deliberately deferred.**

## Read this before using the phrase "two-layer"

It means two different things in this project and the older meaning is the one
grep finds first:

| phrase in context | means |
|---|---|
| `d-kernel-lsm-layer` (2026-08-04) | **PipeWire + kernel.** This memory. The pivot. |
| `d-per-stream-gating` (2026-03-27) | **app-rule + per-stream gating.** A browser-tab problem, entirely inside the PipeWire layer. Predates the pivot by four months. |

That second decision was **renamed on 2026-08-19 from `d-two-layer-model`** to
kill the collision, at Costin's request. `DECISIONS.yaml` carries
`renamed_from:` so a grep for the old id still lands on it. This memory was
renamed from `project-two-layer-pivot` in the same pass.

## Non-obvious traps

- **Docs can be confidently wrong about their own config.**
  `pipewire [pipewire-pulse]` was listed as a DEAD rule in every doc from
  2026-08-04 to 2026-08-23. It is not: `normalize_app_name` strips the trailing
  annotation, so it matches the key `pipewire`, and it had 24 denials to prove
  it. Check a "dead rule" claim by normalising the name, not by reading it.
- **A test can pass with the bug present by coincidence.** The direction-filter
  test for b3 passed with the filter removed, because on this laptop
  `monitor_*` sorts before `playback_*`. Only running it against the
  reintroduced defect caught that.
- **An attribute can be silently absent.** A `#[test]` stacked twice on one
  function left the next one dead — it compiled and read as covered and had
  never run once.
- **Two Firefox builds, different inodes**: `/usr/lib/firefox-esr/firefox-esr`
  (30287776, allowlisted) and `~/firefox-developer/firefox-bin` (1312111, in no
  rule). The kernel keys on inode, so "allowlist Firefox" silently means one
  build. **Firefox-ESR is the agreed test browser.**
- **Enforcement cannot revoke an already-open fd.** The hook is on `open()`,
  not on read. Costin saw live camera video with enforcement on. Real
  limitation, not a bug — say so wherever the camera feature is described.
- `MISSION.yaml` is still frozen at 2026-08-04 and files the kernel layer under
  `what_would_fix_it`, in the conditional. `README.md` still describes the
  helper as hand-started and the default posture as `ask`. **Both are wrong and
  both are the publication blocker.** `ARCHITECTURE.yaml` was realigned and is
  current. `HANDOFF.md` and `ROADMAP.yaml` are the trustworthy pair.
