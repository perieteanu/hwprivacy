Asked on 2026-08-05, after Costin ran `hwprivacy-lsm` in observe mode and had
to ask: *"should i stop it? with ctrl-c?"*

> "modify the script to announce that can be stop ONLY using Ctrl-C and follow
> this rule for next test (announce how the test will end: in spec. time or by
> user SPECIFIC action)"

**Why:** he cannot tell the difference between a tool that is still working
and one that is waiting for him. A wall of startup banner text that happens to
contain "Ctrl-C to detach" is not an announcement — it is a detail he has to
hunt for. Leaving the operator guessing is its own kind of bug, and it wastes a
whole run when he guesses wrong (which already happened: a mic event started
mid-benchmark to "help" contaminated the measurement).

**How to apply — every test, benchmark, or long-running observer must print,
before any work starts, one prominent line saying exactly how it terminates:**

- self-terminating: state the bound (`after 10 cycles, roughly 1 minute`)
- waits for a human: name the exact action AND say nothing else will stop it
  (`press Ctrl-C. Nothing else stops it — no timer, no event limit.`)
- both: say which wins (`whichever comes first`)

Implemented in hwprivacy as `Cli::exit_condition()` in
`hwprivacy-lsm/src/main.rs`, printed as a `HOW THIS ENDS:` line, with
`--duration` and `--max-events` as the self-terminating modes. It is covered by
unit tests so the announcement is a contract rather than a comment — the same
reasoning as [[feedback-measure-before-claiming-cheap]]: prefer a check that
fails over a discipline that must be remembered.

The shell scripts in `~/projects/claude-run/` carry the same line.

This is a general working preference, not hwprivacy-specific. Worth promoting
to `~/.claude/CLAUDE.md` hard preferences if it recurs elsewhere.

On 2026-08-04, told that hwprivacy's daemon burns 1.2% of a core at idle
(polling `pw-dump` twice a second), Costin's response was:

> "the price of 1.2% of a core is very generous. i wouldnt pay such a price."

**Why:** he treats always-on background cost as a first-class design
constraint, not an implementation detail. A 1.2% idle burn was enough to
invalidate an otherwise working architecture. Numbers like this decide
direction for him — so an unmeasured claim of "this is cheap" is worse than
useless, it can steer a whole build wrong.

**How to apply:**
- Measure before asserting overhead. Never say "negligible" from reasoning alone.
- When a number is not yet measured, **say so explicitly** and record it as
  outstanding rather than letting it become a silent assumption. This was done
  in `docs-yaml/ROADMAP.yaml > kernel_layer > outstanding_measurement`, marked
  `NOT YET MEASURED — do not claim it is cheap until it is`.
- Beware the tempting cheap fix that trades the wrong thing: raising
  `poll_interval_ms` buys CPU by widening a security race window. He wants the
  cost gone, not moved.

Still outstanding for hwprivacy: the eBPF LSM hook fires on **every** `open()`
system-wide and its cost has not been measured. Method: time ~200k
`open`/`close` of `/dev/null` with and without the program attached.

On 2026-08-04 hwprivacy changed direction. It was built to police the PipeWire
graph; that was measured and found structurally blind to direct device access.
The project is now **two layers behind one policy engine**:

- **PipeWire layer** (existing, running): monitor taps + per-app/per-stream mic.
  Genuinely works for the playback-monitor case — keep it.
- **Kernel layer** (`hwprivacy-lsm`, new): eBPF LSM on `security_file_open`.
  Sees direct V4L2/ALSA access that PipeWire cannot. **Camera first; audio is a
  separate feature, deliberately deferred.**

State at end of that session: Phase 1 (observe-only) **validated live** — LSM
attached first try, no verifier rejection. Phases 2–4 (enforcement, daemon
integration, systemd) not started.

Do not re-derive any of this. It is written up in the repo:
`docs-yaml/ROADMAP.yaml > kernel_layer` and `> blockers`, plus `CLAUDE.md`.
Read those before proposing anything. See [[reference-kernel-plan-file]] and
[[feedback-measure-before-claiming-cheap]].

Non-obvious trap: the four behavioural defects b1–b4 in the PipeWire layer are
**untouched**, and the deny-vs-ask posture question is still unsettled. Fixing
the kernel layer does not fix those.
