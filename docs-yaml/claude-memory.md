---

When a mechanism has a primary signal and a timeout fallback, **a broken
primary presents as "it works, slowly" — not as a failure.** That is worse than
an outright break, because nothing looks wrong enough to investigate.

Measured 2026-09-01 in hwprivacy. The kernel release path removed a session
keyed on the executable (`firefox-esr`) while the session had been opened under
the rule's name (`firefox`), so `lsm/file_release` matched nothing and did
nothing. `expire_sessions()` then reaped the session 29 s later via
`awaiting_open_secs`:

```
19:56:34  call ended, camera released -> kernel release matched no key
19:57:03  session ended: firefox released Camera   <- the FALLBACK, 29s late
```

The session did end, so the feature appeared to work. It cost an hour.

**Why:** a fallback exists to bound the worst case, not to do the job. When it
starts doing the job routinely, the primary signal is dead and nothing says so.

**How to apply:**
- When a fallback fires where the primary should have, **log it as a warning** —
  it is an anomaly, not a normal path.
- In a test, assert on *which* mechanism ended the thing, not merely that it
  ended. `SESSION_ENDED` arriving is not evidence the release hook works.
- When two code paths derive the same key independently, **extract the derivation
  into one named function and pin it in a test.** Asserting
  `f(x) == f(x)` passes no matter what the call site does — see
  [[feedback-prove-the-test-fails]].

Related: [[project-camera-is-allow-or-deny]], [[feedback-test-the-instrument-not-just-the-code]].

---

Before keeping a new test, reintroduce the defect it exists to catch and watch
it **fail**. A test that passes both ways is worthless, and this is not
theoretical here.

**Why:** on 2026-08-23 the first version of b3's direction-filter test passed
with the filter *removed*. On this laptop a sink's out-ports are `monitor_*`
and its in-ports are `playback_*`, and `monitor` sorts before `playback`, so
mixing the two populations produced the right ordinals by pure alphabetical
luck. The test was rewritten with a port that sorts first. Nothing but running
it against the bug would have found that.

Related: on the same day a `#[test]` attribute was found stacked twice on one
function, leaving the function below it with none. It compiled, it read as
covered, and it had never run once.

## Six failures, and the pattern behind them (2026-08-23)

One in the morning, five that evening. Every single one was an assertion built
on a mechanism I had **assumed** rather than **measured**:

- `an_unset_category_is_not_serialised` — I reintroduced the wrong knob. `toml`
  cannot represent `None` and omits it whatever `skip_serializing_if` says, so
  the attribute proved nothing. The real mechanism was the constructor.
- `set_rule_exe_refuses_what_could_never_match` — one test, three guards whose
  failure modes overlap (a relative path also fails to exist). Removing any one
  still passed. Split into three, one per guard.
- Two `refresh_app_names` GUI tests asserted that rebuilding a dropdown wipes
  what is being typed. Measured instead: `remove_all()` and `append_text()`
  leave a `with_entry` combo's text alone; only `set_active()` touches it. The
  save/restore code under test **could never fire** and was deleted.
- `no UI text offers 'screen'` in the AT-SPI harness passed with the exact
  placeholder bug compiled into the running binary — it scanned `label` nodes,
  and GTK exposes a placeholder as the object attribute `placeholder-text`.
  The check was looking somewhere the defect could not be.

**The tell:** if you cannot name the *measured* mechanism the assertion depends
on, the test is probably pointing at the wrong thing. When the reintroduced
defect does not fail the test, do not just strengthen the assertion — find out
what the mechanism actually is first. Twice that measurement showed the code
under test was dead and the right fix was deletion.

**How to apply:** after writing the test, edit the source to put the bug back
(one line is usually enough), run just that test, confirm FAILED, then revert
and confirm it passes. Do this for each distinct property, not once per file —
five defects were reintroduced separately across the b1/b2/b3 work and each one
mapped to a different failing test. Record in the commit message which defects
were reintroduced. See [[feedback-test-the-instrument-not-just-the-code]].

Built up over 2026-08-05 across three separate confusions, each of which cost a
run or a wrong conclusion. Now a global hard preference in `~/.claude/CLAUDE.md`.

**Who runs what — two axes, `sudo` and `test`. Costin's own formulation:**

    test + sudo  = Costin + banner
    sudo only    = Costin only        (no banner — nothing to interpret)
    test only    = Claude only        (Claude runs it and reads it)

Never hand over a script that does not need `sudo` — run it and report the
conclusion. The banner exists only where Costin must both EXECUTE and
INTERPRET. I first got this wrong twice: once narrowing it to sudo alone, once
widening it to the union. It is the intersection.

**A test+sudo script prints this before any work:**

```
  ─────────────────────────────────────────────────────────────
  HOW THIS ENDS:   <bound, or the named human action>
  RESULTS APPEAR:  <exactly one place — and what is NOT showing them>
  WHAT TO DO:      <paste the ==== marked block into the Claude chat>
  ─────────────────────────────────────────────────────────────
```

**Why each part exists — all three were learned the hard way:**

1. *How it ends* — Costin asked "should i stop it? with ctrl-c?" while an
   observer sat waiting. He cannot distinguish "still working" from "waiting
   for me". Earlier, guessing wrong, he started a mic event mid-benchmark to
   help and contaminated the measurement.
2. *Where results appear* — he asked, correctly, "what burst are you talking
   about? the terminal? firefox popups? the systray app?" I had been describing
   a future notification path as if it existed. **Name the one surface, and
   explicitly rule out the others** — a running tray icon showing unrelated
   events is worse than nothing.
3. *What to do with them* — he works in VS Code + the Claude Code extension and
   pastes output back into the chat. Wrap the pasteable part in
   `════ PASTE FROM HERE ════` / `════ TO HERE ════` so it is one selection.

**Make it a tested contract, not a comment.** In hwprivacy this is
`Cli::exit_condition()` / `results_location()` / `what_to_do()` in
`hwprivacy-lsm/src/main.rs`, with unit tests asserting each part names something
concrete — including that `results_location()` explicitly mentions the tray and
notifications as places results do NOT appear. Same reasoning as
[[feedback-measure-before-claiming-cheap]]: prefer a check that fails over a
discipline that must be remembered.

Supersedes the narrower [[feedback-announce-how-a-test-ends]], which covered
only the first part.

On 2026-08-19, during hwprivacy kernel-layer testing, **four of my own
instruments failed in one evening while the product behaved correctly.** Costin
stopped one run himself with *"i think your proposed test is flawed"*, and he
was right.

**Why:** every one of these produced a confident wrong answer. A test that
reports a conclusion it has not established is worse than no test, because it
gets believed and redirects the whole investigation.

## The four failures, and their shared shape

1. Waited for the log line `attached to lsm/file_open` — which the `--json`
   flag suppresses. The wait could never succeed. It killed a working helper
   and reported it as broken.
2. & 3. Two `pkill -f` / `pgrep -f` patterns matched the **checking shell's own
   command line**. One killed my own process; one reported a helper "running"
   when none existed.
4. A test script killed the helper mid-push, so the request landed on a process
   already shutting down — then deleted the log proving it, because the log
   lived in a `mktemp` dir cleaned by an `EXIT` trap.

**The shape: asserting on log TEXT and on process-name patterns.** Both are
proxies that can be true or false for reasons unrelated to what is being
measured.

## How to apply

- **Assert on STATE, not on text.** Does the socket file exist. Does the kernel
  map hold the key. Is the `open()` actually denied. Text-matching a log line
  is a last resort, and if you must, check the string is reachable under the
  exact flags you are passing.
- **Never delete the raw evidence.** Write logs to a fixed path, not a
  `mktemp` dir with a cleanup trap. A summary chosen in advance only helps if
  you already guessed what mattered — and if you had, you would not have needed
  the run.
- **Suspect the harness first** when a result is surprising. Three separate
  times the product was correct and my measurement was not.
- **Do not make the user the sensor.** A test that asks "did you see video?"
  and provides nowhere to record the answer is broken. Where a human must
  observe, give the observation an explicit slot — and prefer driving it
  yourself (headless Chrome opened the real camera with no human at all).
- **Exclude confounds BEFORE the run, not by argument after.** Prove it by what
  is absent: run with no socket so the daemon *cannot* have helped; check
  nothing already holds the device so a retained fd *cannot* explain it.
- **Distinguish failure modes in error messages.** `recv_timeout` returns `Err`
  for both timeout and disconnect; reporting both as "timed out" made a 0.22s
  disconnect read as a 5s timeout and sent me hunting slow disk I/O that did
  not exist.

Related: [[feedback-test-contract-three-parts]] (how a test announces itself to
Costin), [[project-kernel-pivot]] (where this happened),
[[feedback-measure-before-claiming-cheap]] (the same "measure, don't assert"
instinct applied to cost).

When a doc says the platform *cannot* do something, treat it as an untested
assertion, not a constraint. Check it against the actual kernel, library or
API before designing around it — especially when several documents agree,
because agreement between docs is evidence of copying, not of truth.

**Why:** on 2026-08-23 every doc in hwprivacy, plus the user-visible
notification text itself, asserted **"hwprivacy cannot tell when access ends"**.
It had been repeated since early August and was load-bearing: it was the stated
reason `while_in_use` was unimplementable, and the stated reason the tray
in-use indicator was skipped ("a dot would light and never go out").

Both halves were false.

- **Layer 1 had always seen it.** `main.rs` already diffed live PipeWire link
  ids against tracked connections every poll and pruned the stale ones. A
  vanishing link *is* the release signal. The code was sitting there, used for
  cleanup, and nobody connected it to the claim.
- **Layer 2 could see it too.** `bpf_lsm_file_release` and
  `bpf_lsm_file_free_security` were both present in Debian 13's BTF the whole
  time. One `grep` of `/sys/kernel/btf/vmlinux` settled it in seconds.

Checking took under a minute and unblocked two features that had been written
off as impossible.

**How to apply:** before accepting "X is not possible here", find the primitive
that would make it possible and look for it directly — grep the BTF for a hook,
check the library's symbol table, read the API reference. Then say which you
did. If a claim turns out false, fix it *everywhere* in the same pass: it had
propagated into ADR rationale, ROADMAP entries, code comments and a string the
user actually reads, and each copy would otherwise keep justifying the same
wrong decision.

This is the doc-to-doc propagation failure the global rule already warns about
("verify a doc claim against the filesystem or the host, never against another
document") — applied to a claim about the *platform* rather than about the
project's own code, which is the case that slips through, because it sounds
like background knowledge rather than a project fact.

See [[project-kernel-pivot]] and [[feedback-measure-before-claiming-cheap]].

**The camera takes `allow` or `deny`. `while_in_use` is microphone and playback
monitor only.** Costin's ruling, 2026-09-01, after three live runs in one
evening.

Camera sessions were **built and proved end to end on real hardware** —
allowlist 2 → 3 → 2, live session shown in `hwprivacy-ctl status`,
`SESSION_ENDED` emitted by the kernel — and withdrawn the same evening:

```
20:02:33.712  ALLOWED (first open, count 1)
20:02:33.823  session ended: released the camera (kernel)   [111 ms]
20:02:35.914  12 further allowed open(s)   <- the ACTUAL capture
20:02:38.317  executable removed from the allowlist, MID-CALL
```

Firefox **probes** the camera before capturing — open, close, then open the
handles it records with. The probe close takes the open count to zero, so the
release fires before capture begins. The call survived only because the capture
opens beat the allowlist removal by ~2.5 s: **the video worked by race, not by
policy.**

**The model was wrong, not the code.** "A camera session is 13 opens" was
measured as a *burst* on 2026-08-05 and quietly became the design. An open
count is a **transient**: zero means "no handle held right now", not "the
application has finished with the camera".

What survived and is worth keeping:

- the **actionable camera prompt** (Always Allow / Always Deny), so a camera can
  be granted from the notification instead of hand-editing `config.toml`
- `RETRY_HINT` — even *Always Allow* applies to the NEXT attempt, because the
  `open()` that raised the prompt was refused before anyone saw it
- the `lsm/file_release` BPF program stays **attached**: verifier-accepted,
  events arrive regardless, and it is the working half

Reopening it needs a way to tell "the count reached zero" from "the device was
released". Do **not** reach for `awaiting_open_secs` — it bounds a session that
was never opened, and using it here masks the defect. See
`ROADMAP > camera-session-ends-on-the-probe-close` and ADR
`d-camera-is-allow-or-deny`. Related: [[project-kernel-pivot]].

**hwprivacy's layer 1 no longer polls.** `pw-dump --monitor` replaced spawning
`pw-dump` twice a second, on 2026-09-02.

```
idle CPU        2.70-2.82% of a core  ->  0.033%   (82x)
link latency    0-500 ms window       ->  11 ms
```

Measured on the live service, cgroup `CPUUsageNSec` over wall time — the same
method every earlier CPU figure in this project used.

**`pipewire-rs` was considered and lost, but not on the numbers.** Its recorded
objection in `d-event-driven-substrate` — MSRV, a new dependency — is obsolete:
`librust-pipewire-dev 0.8.0-7` is packaged in Debian 13. It lost because the
`--monitor` wire format is *already* what the daemon wanted: block 0 is a
complete snapshot in `GraphSnapshot`'s exact shape, later blocks carry only
changed objects, and a removal is the object with `"info": null`.
`parse_node`/`parse_port`/`parse_link` are reused unchanged.

**The trap that shaped the whole design**, measured before any code was
written: **`pw-dump --monitor` dies when PipeWire restarts, and exits 0.** A
clean exit is indistinguishable from success, so a bare child would leave the
daemon permanently blind while every status surface reported healthy — blocker
b5's exact shape. The polling design was immune because it respawned every
tick, and that resilience had to be rebuilt deliberately:

- any exit is an anomaly, **including 0**
- a respawn **re-seeds, never merges** — PipeWire ids are not stable across a
  server restart, so a merged graph carries dead ids a new object can reuse
  ([[project-camera-is-allow-or-deny]] shares that b2 hazard)
- a watchdog covers silence, because a wedged reader and a quiet system look
  identical

`poll_interval_ms` is retired: kept with `skip_serializing` so an existing
config still loads, ignored, dropped on the next rule write.

Nothing downstream changed — policy, config, D-Bus, the frontends and the
kernel layer are untouched, because `GraphState::snapshot()` hands out the same
type everything already consumed. ADR: `d-monitor-stream-not-polling`.
Related: [[feedback-measure-before-claiming-cheap]].

On 2026-08-04 hwprivacy changed direction. It was built to police the PipeWire
graph; that was measured and found structurally blind to direct device access.
It now has **two enforcement layers behind one policy engine**:

- **PipeWire layer** (existing, running): monitor taps + per-app/per-stream mic.
  Genuinely works for the playback-monitor case, which has no kernel
  equivalent — keep it.
- **Kernel layer** (`hwprivacy-lsm`, `hwprivacy-proto`): eBPF LSM on
  `security_file_open`. Sees direct V4L2/ALSA access that PipeWire cannot.
  **Camera first; audio is a separate feature, deliberately deferred.**

grep finds first:

| `d-per-stream-gating` (2026-03-27) | **app-rule + per-stream gating.** A browser-tab problem, entirely inside the PipeWire layer. Predates the pivot by four months. |

That second decision was **renamed on 2026-08-19 from `d-two-layer-model`** to
kill the collision, at Costin's request. `DECISIONS.yaml` carries

`PolicyFingerprint`, which also closed the fact that **`SetPolicy` was only
ever sent at connect time**, so rule changes from ctl/tui/gui never reached the
kernel at all.

## State as of 2026-08-23 EVENING — permissions were rebuilt

Costin deleted every rule, tried a Firefox video call, and could not grant the
camera back. That found four defects and led to three commits: `ef8e5e5`,
`e6217c5`, `bf38ab6`. **188 tests** (was 152). The `hwprivacy-lsm` binary in
`/usr/bin` is still the 08-19 build — the new one needs `sudo` to install.

What the permission model is now:

- **Rule categories are `Option<Permission>`.** Unset falls through to
  `default_action`, printed as an em dash, never "deny". `set_rule` used to fill
  all three with `Deny`, so granting a camera silently muted the microphone.
- **`exe_path` is writable** — `SetRuleExe` / `AllowCamera` over D-Bus,
  `rules allow-camera <path> --as <rule>` on the CLI, and a click in the GUI.
  Before this **no string typeable in any frontend could grant a camera**,
  because `kernel_camera_allowlist()` keys on `exe_path` alone. The picker is
  the kernel's own denial log; it already recorded the path.
- **`mic1`/`mic2` are GONE** (`d-one-device-one-prompt`). They labelled two
  CHANNELS of one microphone, and `device_instance()` could only ever label
  channels — it filtered siblings by `node_id`, and two real microphones are
  two nodes. Worse, the exemption they justified meant the second channel hit
  the b6 guard and was denied on *every* attempt.
- **`ask_each` is GONE** (`d-no-per-stream-grants`). It could never work: the
  link is destroyed before the user is asked, `link_manager` can only destroy,
  and the grant was keyed on a node id pruned the moment the stream left the
  graph. The string still parses, to `ask`, so old configs load.
- **`while_in_use` is a real session** (`d-while-in-use-is-a-session`). It was
  a synonym for `allow` — `while_in_use_streams` written and read nowhere. Now:
  no session → ask; the session ends on release; the next open asks again.
  Keyed on **(app, device)**, and `policy.while_in_use_settle_secs` bridges the
  gap between the answer and the app's reconnect.
- **The camera has sessions too** (`d-camera-sessions-via-file-release`), via a
  second BPF program on `lsm/file_release`. The grant IS presence in the kernel
  allowlist, added while live and removed on release. **UNVERIFIED — the BPF
  verifier has never seen it.** Run
  `~/projects/claude-run/hwprivacy-camera-sessions-20260823.sh`.
- **`make gui-test`** — 14 AT-SPI checks driving the live GTK window. The three
  frontends had zero tests before.

## Non-obvious traps

- **Docs can be confidently wrong about their own config.**
  `pipewire [pipewire-pulse]` was listed as a DEAD rule in every doc from
  2026-08-04 to 2026-08-23. It is not: `normalize_app_name` strips the trailing
  annotation, so it matches the key `pipewire`, and it had 24 denials to prove
  it. Check a "dead rule" claim by normalising the name, not by reading it.
- **A test can pass with the bug present by coincidence.** The direction-filter
  test for b3 passed with the filter removed, because on this laptop
  `monitor_*` sorts before `playback_*`. Only running it against the
  reintroduced defect caught that.
- **An attribute can be silently absent.** A `#[test]` stacked twice on one
  function left the next one dead — it compiled and read as covered and had
  never run once.
- **Two Firefox builds, different inodes**: `/usr/lib/firefox-esr/firefox-esr`
  (30287776, allowlisted) and `~/firefox-developer/firefox-bin` (1312111, in no
  rule). The kernel keys on inode, so "allowlist Firefox" silently means one
  build. **Firefox-ESR is the agreed test browser.**
- **Enforcement cannot revoke an already-open fd.** The hook is on `open()`,
  not on read. Costin saw live camera video with enforcement on. Real
  limitation, not a bug — say so wherever the camera feature is described.
- `MISSION.yaml` is still frozen at 2026-08-04 and files the kernel layer under
  `what_would_fix_it`, in the conditional. `README.md` still describes the
  helper as hand-started and the default posture as `ask`. **Both are wrong and
  both are the publication blocker.** `ARCHITECTURE.yaml` was realigned and is
  current. `HANDOFF.md` and `ROADMAP.yaml` are the trustworthy pair.

See [[reference-kernel-plan-file]], [[feedback-measure-before-claiming-cheap]]
and [[feedback-verify-platform-claims]] — that last one is what unblocked
`while_in_use` and camera sessions.
